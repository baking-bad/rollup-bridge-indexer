Where the outbox levels live

One index walks two chains that answer separately. What it has learned from the first and not yet done about the second is the only state a crash can silently destroy — and for a long time that state existed in exactly one place: process memory.

Two sources, one cursor

TzKT serves the inbox — the L1 messages addressed to the rollup. The rollup node serves the outbox — the messages coming back out, one request per L1 level. Nothing connects them but this index.

Walking the inbox is what discovers outbox work: every external message means its level has outbox messages to fetch. So a pass always runs in that order — learn from TzKT, then ask the node. And the resume cursor is not stored anywhere of its own; it is derived from the inbox rows already committed, as max(id).

That is the whole shape of the problem. Committing an inbox row advances the cursor past the message that taught us about an outbox level. If the level has not been fetched by then, nothing will ever ask again — and nothing reports it. The index says realtime, dipdup_head sits at the chain head, and the row is simply absent.

The queue is written before the rows that move the cursor past the externals that filled it, and cleared after the rows it produced are committed. Between those two points a crash costs a re-fetch and never a message.

Three ways the picture was wrong

Each one loses messages permanently and reports nothing. They sit at different points of the same pass.

at step 04 → 05

The queue had nowhere to live

The rows were committed first and the levels drained afterwards. A drain that died came back with its cursor above the externals it had never served.

On 2026-08-20 a node stopped applying blocks while still answering RPC. 20 outbox messages present on the node were absent from the database, and their withdrawals could not match. The level that failed was one of them; the rest had already been fetched into a batch that was never flushed.

- rows → drain + queue → rows → drain → queue
at step 05

The ceiling was the wrong chain

The drain refused levels above the L1 head — but the request goes to the rollup node, which applies L1 blocks on its own schedule and can lag arbitrarily while still answering RPC. That is the fault itself.

The node's own global/block/head/level is exact: that level answers 200, the next answers 500 kind: temporary. A level above it is now deferred and stays owed, like a level the chain has not produced.

- min(queue) <= _realtime_head_level + min(queue) <= node applied level
at step 02

One message skipped per restart

The fetch filters id.gt=, so the cursor means the last id consumed — which is what the in-run advance stored. Both places that derived it from persisted state stored the next id wanted instead.

The message on that boundary was requested by neither run. Raw TzKT ids are contiguous, so a restart mid-page lands on a real message in 88% of cursor positions; a fresh database lost the first message of its window every time.

- cursor = 1 + max(id) + cursor = max(id)

Why not one transaction

The alternative is to commit the inbox rows and the outbox rows atomically and let the queue stay a local variable. It does not pay here.

On the realtime path the writes are already atomic — the head index opens the transaction around the handler, and the handler deliberately does not ("Handlers are not atomic, levels are"). The only path that would gain is the backfill, where system hooks run with atomic=False — and that is where page-atomicity is unaffordable: one 10 000-message page spans ~1100 distinct L1 levels, so ~1100 sequential node requests would all have to succeed before anything commits, across ~5 500 pages on mainnet.

That trades a data-loss bug for a liveness failure in the one operation that repairs data loss — the reindex.

Still not covered

  • The dipdup_meta write is untested against Postgres; the stand case and the unit tests both run on sqlite.
  • A reorg rollback cannot revert the stored queue — Meta is a plain Tortoise model and produces no dipdup_model_update rows. The cost is re-fetches, which the outbox ignore_conflicts absorbs.
  • A reorg also leaves the in-memory cursors above reverted rows. That predates all of this and is not addressed; the fix is to re-derive them in on_index_rollback.
  • That a stopped node reports its frozen applied level rather than an advancing one follows from what the endpoint means, and was verified as an exact boundary on a healthy node — but never observed on a broken one.
