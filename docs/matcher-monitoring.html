Мониторинг матчинга
#305 · #312

Два монитора каждые 5 минут проверяют один инвариант данных: ни одна операция моста не живёт без связки, которую ставит матчер, дольше часа. Это единственная защита от отказа «всё индексируется, но не матчится» — все остальные мониторы такой отказ не видят. #305 держит депозиты, #312 — выводы. Документ описывает задеплоенную конфигурацию (сверена с Kuma дословно) и относится только к mainnet prod; порядок действий при срабатывании — в разделе «триаж».

дыра

Регрессия матчинга невидима процессным мониторам

четыре элемента приложения — и один из них без собственного сигнала

Функционально индексер делает четыре вещи: индексирует L1 (Tezos), индексирует L2 (Etherlink), матчит ноги обеих сторон в единые операции моста и отдаёт результат через API (Hasura). Первые два элемента — процессы: их здоровье видно по свежести голов и по потоку операций, и именно это проверяет ONLINE-монитор #187. Четвёртый проверяется любым запросом к эндпоинту.

Матчинг — не процесс, а результат: строки уже проиндексированы, вопрос лишь в том, связал ли их движок. Деплой, в котором матчинг сломан регрессией — шаг выпал из batch-цикла, лок перестал взводиться, изменилась схема, — оставляет #187 зелёным: блоки приходят, операции пишутся, API отвечает. Единственный след живёт в данных: у операций не появляется вторая нога, и потребители API (мостовой UI, эксплорер) бесконечно показывают депозиты «в пути». #305 и #312 созданы закрыть ровно эту дыру: они смотрят не на процесс, а на сами данные.

Напрашивающаяся альтернатива — алертить по статусу («есть операция в CREATED дольше часа») — не работает: у вывода CREATED означает сразу две вещи — и «матчер ещё не связал» (авария), и «связан, легитимно ждёт ~2 недели исполнения на L1» (норма; сейчас так ждут 765 выводов). Поэтому сигналом выбрано поле-связка, а не статус — об этом следующий раздел.

механика

Сигнал — поле, которое ставит только матчер

путь операции по коду · handlers/bridge_matcher.py

У депозита якорь — строка bridge_deposit, которую матчер создаёт из L1-ноги; связка — поле l2_transaction_id. У вывода якорь — L2-нога l2_withdrawal; связка — outbox_message_id в её bridge_withdrawal. Оба поля заполняются только матчером и любым из его путей (FA по координатам inbox, XTZ по счёту-сумме-окну, Michelson по восстановленному op-hash) — один признак покрывает все пути без пути-специфичных проверок.

ДЕПОЗИТ · L1 → L2 · зона #305 = шаги 1–3

L1-депозит проиндексированtezos-индексы

Матчер создаёт bridge_deposit с пустой связкой (l2_transaction_id = NULL) и операцию в статусе CREATED. С этого момента идёт отсчёт возраста по времени цепочки.

По хэшу параметров и уровню; координаты inbox — то, по чему ищется L2-нога. Если inbox-индекс встал, матчинг слепнет — за этим отдельно смотрит #313.

1

L2-burn проиндексированevm-индексы

Матчер создаёт bridge_withdrawal с пустой связкой (outbox_message_id = NULL) и операцию в статусе CREATED.

2

Привязан ответ ролапа — outbox-сообщениеэто ждёт #312 · норма ≤5 мин

По хэшу параметров; outbox_message_id заполнен. Измерено: p99 = 42 c, максимум ~5 мин. Работа матчера по выводу на этом закончена.

3

Ожидание цемента и исполнение на L1не мониторится — протокол

~2 недели до цементирования, затем execute на L1 и статус FINISHED. Это скорость протокола, а не индексера; сейчас здесь легитимно ждут 765 выводов — потому зона #312 заканчивается на шаге 2.

Оба монитора спрашивают одно: есть ли операция, которая вышла из своей зоны по возрасту, но связки так и не получила. Порог — 1 час при измеренной норме в десятки секунд: запас минимум ×12 от худшего измеренного случая, поэтому в штатной работе мониторы не звенят вовсе.

правило

Дословно: запрос, критерий и почему границы такие

POST /v1/graphql · критерий JSONata должен дать true · опрос 300 c · 2 ретрая

── #305 Bridge Matcher Mainnet · тело запроса ──────────────────────────
{ unmatched: bridge_deposit(
    where: {l2_transaction_id: {_is_null: true}},
    order_by: {l1_transaction: {timestamp: desc}}, limit: 100)
  { l1_transaction { timestamp } } }
── критерий (JSONata, ожидается true) ──────────────────────────────────
$count(data.unmatched[
  $millis() - $toMillis(l1_transaction.timestamp) > 60*60*1000 and
  $millis() - $toMillis(l1_transaction.timestamp) < 7*24*60*60*1000
]) = 0

Читается так: среди 100 свежайших депозитов без L2-ноги нет ни одного, чья L1-операция случилась от часа до недели назад. Есть хотя бы один — монитор Down.

── #312 Bridge Withdrawal Matcher Mainnet · тело запроса ───────────────
{ stuck: l2_withdrawal(
    where: {_not: {bridge_withdrawals: {outbox_message_id: {_is_null: false}}}},
    order_by: {timestamp: desc}, limit: 100)
  { timestamp } }
── критерий (JSONata, ожидается true) ──────────────────────────────────
$count(data.stuck[
  $millis() - $toMillis(timestamp) > 60*60*1000 and
  $millis() - $toMillis(timestamp) < 7*24*60*60*1000
]) = 0

Читается так: нет ни одного L2-вывода возрастом от часа до недели, у которого ни одна строка bridge_withdrawal не привязана к outbox-сообщению. Условие через _not покрывает оба отказа сразу: строка-связка не создана вовсе или создана, но outbox не привязан.

Возраст считается по времени цепочки, не по времени записи. Окно по created_at ломается на каждом бэкфиле и реиндексе: исторический хвост записывается заново, старые операции выглядят «свежими», и монитор краснеет днями на данных многомесячной давности. Время цепочки (l1_transaction.timestamp у депозита, timestamp burn-а у вывода) от переиндексации не меняется.

Нижняя граница 1 час — из измерений выше: запас ×12 и больше от худшего случая, ложных срабатываний от штатной работы нет, а деградация видна не позже чем через час. Верхняя граница 7 дней — из-за постоянного осадка: на проде живут 500 депозитов, у которых L2-ноги не будет никогда (ядро ролапа отвергло депозит; все 500 — в терминальном статусе FAILED_INBOX_MATCHING_TIMEOUT, новейший по времени цепочки — 2026-02-14). Критерий статус не проверяет, поэтому без верхней отсечки монитор был бы красным всегда — то есть бесполезным. Окно делает базовую линию нулевой: сейчас в зоне #305 — 0 операций, в зоне #312 — 0, и у выводов осадка нет вовсе (все 28 211 связаны).

У окна две известные цены. Операция, застрявшая дольше недели, выпадает из окна и монитор гаснет — но к этому моменту он звенел ~7 суток подряд, пропустить это сложно. И свежий отвергнутый ядром депозит честно продержит #305 красным до 7 суток, хотя матчер исправен, — за всю историю наблюдений таких не случалось, а случись — на такой депозит всё равно нужно смотреть глазами: для пользователя он потерян.

Задержка обнаружения. Критерий по построению срабатывает через час после первой пострадавшей операции; опрос каждые 300 c и 2 ретрая добавляют ещё ~10–15 мин до статуса Down. И главное: мониторы питаются реальным трафиком — сломанный матчер при нулевом потоке операций не звенит, сигнал появится с первым же депозитом или выводом после поломки. На мейннете операции идут ежедневно, так что на практике это обнаружение день в день.

Асимметрии таблицы — следствие выбора якоря, и они намеренные. #305 якорится на L1-строках: если L1-индексация встала, новые bridge_deposit не создаются, зоне нечем наполняться и монитор остаётся зелёным — остановку L1 ловит #187. Зато содержимое L2-ноги депозитов #305 проверяет глубже, чем #187: тот видит только «процесс жив и головы свежи», а #305 — что конкретные депозиты реально получили свою L2-строку. Зеркально у #312: остановка L2-индексации для него невидима (нет burn-ов — нет кандидатов), это тоже зона #187.

Чего эта пара не покрывает, даже в своей колонке: она проверяет наличие связки, а не её корректность — операция, сшитая с чужой ногой, для мониторов неотличима от правильной; проверка качества матчей — это разовые сверки данных, не алертинг. И вся пара существует только на mainnet prod: staging и обе shadownet-сборки мониторинга матчинга не имеют.

Итог для владельца проекта: пара #305/#312 — это не дубликат ONLINE-мониторинга, а единственный сигнал о третьем элементе приложения, том самом, ради которого индексер существует (его продукт — сматченные операции моста). Побочно она добавляет полезную избыточность по L2-ноге и rollup-каналам. Стоимость владения — ноль: конфигурация статична, секретов не требует (Hasura читается анонимно), базовая линия — ноль срабатываний в штатной работе.
