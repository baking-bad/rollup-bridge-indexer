# Эксплейнер: модели L2 Michelson vs L2 EVM — разделять или нет

Статус: **draft для обсуждения** (2026-06-12). Цель — зафиксировать, где именно
смешались модели/примитивы двух L2-рантаймов, какие варианты есть, и выбрать один.

## Как мы сюда попали

Индексер проектировался под один L2 — EVM (Etherlink). Tezos X добавил на L2
второй рантайм — Michelson (Tezlink): XTZ-депозит с tz1-получателем приземляется
на L2 как синтетическая псевдо-Michelson-операция. Чтобы не дублировать схему,
эти операции записываются в ту же таблицу `l2_deposit`
(`EtherlinkDepositOperation`), переиспользуя EVM-поля «по аналогии». Аналогия в
нескольких местах натянутая.

## Инвентаризация смешения

Одна таблица `l2_deposit`, два класса строк. Семантика полей расходится:

| Поле | EVM-строка | Michelson-строка |
|---|---|---|
| `transaction_hash` (Char 64) | голый 64-hex tx-hash | base58 `o…` op-hash (51 симв.) |
| `transaction_index` | индекс tx в блоке (малое число) | Tezos `counter` аккаунта (огромное, только для ordering) |
| `log_index` | индекс лога | всегда `NULL` |
| `address` (Char 40) | hex-40 отправителя без `0x` | base58 `tz1…` отправителя (36 симв.) |
| `l2_account` (Char 40) | hex-40 получателя | base58 `tz1…` получателя |
| `amount` (Text) | wei (native) / raw token amount | **mutez × 10¹² при записи** (`WEI_PER_MUTEZ`), чтобы выглядело как wei |
| `level` | номер EVM-блока Etherlink | Tezlink-уровень (⚠ соответствие EVM-блокам не проверено — см. открытые вопросы) |
| `l2_token` FK | `EtherlinkToken('xtz', decimals=18)` | тот же токен, хотя нативная единица рантайма — mutez (6 знаков) |

Класс строки **нигде не хранится явно** — он выводится по конвенциям:

- `michelson_matcher.py:41` — Michelson-строки = `transaction_hash__startswith='o'`;
- `bridge_matcher.py:148` — value-zip-шаг **исключает** их тем же префиксом;
- `bridge_matcher.py:96` — coords-шаг отличает свои строки по `inbox_message_level__isnull`;
- `BridgeOperation.l2_account` — hex-40 или `tz1…` в одной колонке, отличимы только по виду строки.

Единицы тоже конвертируются строковой магией, рассыпанной по коду:

- `bridge_matcher.py:162` — `l2_deposit.amount[:-12]` (wei → mutez срезом строки);
- `bridge_matcher.py:316` — `full_amount * int(1e12) == int(amount)`;
- `rollup_message.py:552` — `int(str(payload.amount)[:-12])`;
- `handlers/tezos_x/on_michelson_deposit_ophash.py:57` и `…/on_michelson_deposit.py:93` — `op.amount * WEI_PER_MUTEZ`.

Именование уже признано неточным в самом коде: `EtherlinkDepositOperation`
хранит не-Etherlink строки, в `tezos_x/on_michelson_deposit.py:99` лежит
`TODO(rename)`.

## Цена, которую уже заплатили

**2026-06-11, tezosx-shadownet: все 12 L2 Michelson-депозитов слинковались с
чужими L1-ногами и были помечены `finished`** (фикс `9b36cc5`). Причина — ровно
это смешение: generic-шаги матчера претендовали на строки, для которых у них нет
ключа, потому что «класс строки» — неявная конвенция, а не свойство данных.
Фикс добавил guard'ы (`isnull`-фильтр + исключение по префиксу `o`), т.е. ещё
больше конвенций поверх конвенций. Это работает, но каждый новый шаг матчера
обязан помнить про все классы строк, иначе — повторение инцидента.

## Факты, ограничивающие решение

1. **Michelson-поверхность мала и расти не будет** (scope-решения Tezos X):
   - FA-токены на Michelson — DECIDED, не появятся. Только XTZ.
   - Выводы с Michelson идут через NAC от EVM-алиаса → это обычные EVM-withdrawal.
     Отдельной Michelson-withdrawal-модели не нужно.
   - Итого: «вторая модель» нужна ровно для одного потока — XTZ-депозиты.
2. **Принятое решение `L2Account`** (KB: `decisions/deposit-model-design.md`,
   Опция 3): нормализованная таблица адресов с `kind = EVM | TZ | EVM_ALIAS`,
   `l2_account` становится FK. Оно уже закрывает измерение «формат/тип адреса»
   и предполагало **одну** таблицу операций. Тогда же отдельная
   `MichelsonDepositOperation` рассматривалась и была отклонена — но только в
   разрезе адресов, до того как смешение единиц/хэшей стало реальностью.
3. **Op-hash-матчер — production-механизм без планов на удаление** (event-based
   альтернатива в `tezos_x/on_michelson_deposit.py` лишь держит опцию открытой —
   upstream ничего не обещал). Важно: даже если когда-нибудь матчер заменится
   событиями, смешение не исчезнет — event-based хендлер пишет в ту же таблицу
   в той же форме.
4. **Окно дешёвой миграции — до mainnet-апгрейда (25 июня)**. Сейчас
   Michelson-строки есть только на тестовых сетях; после апгрейда mainnet любая
   смена схемы потребует миграции боевых данных.
5. **Потребители хотят единый поток**: bridge UI, Hasura GraphQL, Kuma-мониторинг
   читают `l2_deposit` / `bridge_operation` как один список, не зная рантаймов.

## Два независимых вопроса

Их стоит решать по отдельности — любая комбинация осмысленна:

- **Вопрос T (таблицы):** одна таблица L2-депозитов или две?
- **Вопрос U (единицы):** хранить amount в wei для всех или в нативной единице рантайма?

---

### Вопрос T — структура таблиц

#### T0. Статус-кво + гигиена (только rename и докуметация)

Переименовать `EtherlinkDepositOperation` → `L2DepositOperation` (и
`set_pending_etherlink_deposits` → `set_pending_l2_deposits`), задокументировать
конвенции. Схема БД не меняется.

- Плюсы: почти бесплатно; убирает враньё в имени.
- Минусы: классы строк остаются неявными; следующий шаг матчера снова может
  «забыть» про guard — инцидент 06-11 ничем не предотвращён структурно.

#### T1. Одна таблица + явный дискриминатор `l2_runtime`

Колонка `l2_runtime = EnumField(L2Runtime)  # evm | michelson` (заполняется
хендлером, который и так знает, кто он). Все guard'ы матчера переводятся с
`startswith('o')` / `isnull`-эвристик на честный фильтр по enum. Опционально
туда же — `l2_runtime` в `BridgeOperation` для фильтрации в UI/мониторинге.

- Плюсы: класс строки становится свойством данных, а не конвенцией; дисджойнтность
  пулов матчера выражается одним фильтром и проверяется тестом; дешёвая миграция
  (одна колонка, бэкфилл по тому же префиксу `o` один раз); совместимо с принятым
  решением `L2Account` (адресное измерение) и с единым потоком для потребителей;
  ничего не ломается в Hasura — поле добавляется, не меняется.
- Минусы: семантика «пустых» полей (`log_index=NULL`, `transaction_index=counter`)
  остаётся натянутой; в одной колонке по-прежнему два формата хэшей и (до
  `L2Account`) два формата адресов.

#### T2. Разделить: отдельная `MichelsonDepositOperation` (l2_michelson_deposit)

Своя таблица со своими полями (`op_hash`, `counter`, `tz`-адреса, mutez).
`BridgeDepositOperation` получает второй nullable-FK `l2_michelson_transaction`
(полиморфных FK в Tortoise нет) + check-constraint «ровно один из двух».

- Плюсы: каждый рантайм типизирован честно, никаких полей-оборотней; матчер-шаги
  физически не могут перепутать пулы.
- Минусы: polymorphic-боль в каждом потребителе — UI/Hasura/мониторинг должны
  UNION-ить две таблицы и обрабатывать два FK; дублирование схемы ради
  **одного** потока (только XTZ-депозиты, см. факт 1); противоречит уже принятому
  `L2Account`-решению (его аргумент «retroactive alias через JOIN» работает,
  когда операции в одной таблице); самый большой объём работ; depositы на
  EVM-алиас tz-юзера снова поднимают вопрос «в какую таблицу писать».

### Вопрос U — единицы хранения amount

#### U0. Wei для всех (статус-кво)

Michelson-строки конвертируются при записи (`mutez × 10¹²`).

- Плюсы: потребители видят одну шкалу, ничего не пересчитывают; согласуется с
  `EtherlinkToken('xtz').decimals = 18`; так уже работает и кернел сам считает
  депозит в wei (`eth_from_mutez`) — хранимое значение совпадает с L2-реальностью EVM-вида.
- Минусы: 12 хвостовых нулей — фиктивная точность; обратные конверсии в коде —
  строковые срезы `[:-12]` (3 места), хрупко; «нативная правда» Michelson-рантайма
  (mutez) в БД отсутствует.

#### U1. Нативные единицы + самоописание через токен

Michelson-строки хранят mutez и ссылаются на отдельный токен-row (например,
`xtz-tezlink`, `decimals=6`); потребитель всегда нормализует через
`l2_token.decimals`, как уже делает для FA-токенов.

- Плюсы: в БД лежит правда; никакой фиктивной точности; конверсия выражена
  данными (decimals), а не магией в коде.
- Минусы: ломает потребителей, которые сейчас «знают», что xtz = 18 знаков;
  агрегации по xtz должны учитывать два токен-row; матчеру всё равно нужна
  конверсия для сравнения с L1 (mutez) — выигрыш в коде меньше, чем кажется;
  миграция значений, а не только схемы.

#### U2. Wei + явные хелперы конверсии (компромисс)

Хранение как в U0, но все `[:-12]` / `* 1e12` заменяются на пару функций
`wei_to_mutez` / `mutez_to_wei` с проверкой делимости (остаток ≠ 0 → лог/ошибка,
а не молчаливый срез).

- Плюсы: убирает хрупкость строковых срезов без миграции и без ломки потребителей.
- Минусы: фиктивная точность остаётся; это рефакторинг кода, не решение модели.

## Сравнение (вопрос T)

| Критерий | T0 гигиена | T1 дискриминатор | T2 split |
|---|---|---|---|
| Защита от повторения инцидента 06-11 | нет | да (фильтр по enum + тест) | да (физически) |
| Объём работ | XS | S (колонка + бэкфилл + guard'ы) | L (таблица, dual-FK, все потребители) |
| Ломает потребителей (UI/Hasura/Kuma) | нет | нет | да (UNION, два FK) |
| Согласованность с решением `L2Account` | нейтрально | да | конфликтует |
| Честность типов полей | нет | частично | полностью |
| Оправдан при «Michelson = только XTZ-депозиты» | — | да | избыточен |

## Рекомендация (моя, на обсуждение)

**T1 + U2, и сделать rename из T0 заодно**: одна таблица `L2DepositOperation`
с явной колонкой `l2_runtime`, wei как единая шкала хранения, конверсии — через
checked-хелперы вместо `[:-12]`. Плюс `l2_runtime` продублировать в
`BridgeOperation` для UI/мониторинга.

Логика: главный реальный риск — неявные классы строк в матчере (инцидент 06-11),
и его закрывает дискриминатор, а не split. Split (T2) платит polymorphic-цену во
всех потребителях ради единственного потока, который к тому же не будет расти
(FA на Michelson не будет, withdrawals идут через NAC как EVM). Если когда-нибудь
Michelson-поверхность расширится — T1 не мешает мигрировать на T2: дискриминатор
как раз даст чистый критерий разреза.

U1 (нативные mutez) стоит выбирать только если решим, что «БД хранит правду
рантайма» важнее стабильности потребителей — это в первую очередь продуктовый
вопрос к UI.

Сделать это стоит **до mainnet-апгрейда 25 июня** — пока Michelson-строки есть
только на тестовых сетях и бэкфилл тривиален.

## Открытые вопросы к обсуждению

1. Согласны ли с T1 против T2 при текущем scope (Michelson = только XTZ-депозиты)?
2. U: нужна ли потребителям (UI) «нативная» mutez-величина, или wei-шкала всем удобнее?
3. `level` у Michelson-строк — Tezlink-уровень. Совпадает ли он с номером
   EVM-блока на Tezos X (одни блоки секвенсера или разные)? Влияет на смысл
   ordering `('-level', '-transaction_index', …)` в смешанной таблице.
4. Куда класть `l2_runtime` бэкфилл-миграцию — SQL в `sql/` при деплое или
   разово руками (строк пока десятки, только тестовые сети)?
5. Делать ли rename моделей/локов (`TODO(rename)` в коде) в том же PR или отдельным?
